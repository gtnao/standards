# Forms and translations

Use React Hook Form, `@hookform/resolvers/zod`, Zod and Mantine. Put page forms in `_components/` and their schemas in the nearest `_helpers/form-schema.ts`.

- Connect Mantine inputs with `Controller`. Read `fieldState.error?.message`; do not traverse union-shaped errors or cast a form context to a narrower branch.
- Model conditional field presence and requirements with `z.discriminatedUnion`. Do not add `z.unknown()` fields solely to make error access compile.
- Use `refine` or `superRefine` for cross-field rules and attach issues to the intended field path. Revalidate affected fields when providing feedback on change.
- Use `useForm<z.input<typeof schema>, unknown, z.output<typeof schema>>`. Default values and input controls use the input type; successful submission uses the output type.
- Check complete initial values with `satisfies FormInput`. Give conditionally mounted controls a defined initial value too.
- Use `useWatch` for reactive rendering, including with React Compiler. Do not use `getValues` as a reactive subscription.
- Keep hidden values by default. Unregister only when the interaction requires discarding them. Consider field-array reorder behavior before using `shouldUnregister`.
- Submit parsed values from `handleSubmit`; ordinary Zod objects strip fields absent from the active union branch.
- Revalidate received data on the server before calling usecases.

Text inputs usually accept `field` directly. Checkboxes and switches need `checked` and `event.currentTarget.checked`. Select inputs need an explicit empty state such as `null`. NumberInput can produce strings for empty and intermediate states; reject emptiness before numeric coercion. Preserve `onBlur`, `name` and `ref` when adapting controls. Do not combine `register` and `Controller` on one input.

Start with standard hooks and components. Add shared wrappers only when duplication warrants them, preserving input/output and field-path types without resolver casts.

## Translation contract

Keep messages in `messages/ja.json`; start with Japanese only and no locale URL or proxy.
Use lowerCamelCase keys at every level. Name the translation function `translate` and always pass full keys:

```ts
const translate = useTranslations();
translate("validation.required");
```

Use `await getTranslations()` in async Server Components. Never shorten the variable to `t` or pass a namespace to either translation API.
Message declarations are generated by the next-intl plugin. Do not edit or commit `messages/*.d.json.ts`. Run `pnpm run typecheck` to generate route and message types before checking.

Schema factories receive translated strings, not a next-intl dependency:

```ts
export function createFormSchema(messages: { required: string }) {
  return z.object({
    name: z.string().trim().min(1, { error: messages.required }),
  });
}
```

```ts
const schema = createFormSchema({
  required: translate("validation.required"),
});
const resolver = zodResolver(schema, {
  error: () => translate("validation.invalid"),
});
```

Keep translation calls typed, including interpolation arguments. Pass translated messages through Zod to Mantine. Do not cast an error string to a translation key or change global `z.config()` per form/request. For server validation, construct the same schema using `getTranslations()` and provide a per-parse fallback error map.
