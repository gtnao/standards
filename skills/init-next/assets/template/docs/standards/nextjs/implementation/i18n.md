# 翻訳の実装方針

[next-intlの導入](../setup/i18n.md)を前提に、文言と呼び出し方を揃える。

## キーの分類と命名

`messages/ja.json`に文言を定義する。キーは各階層ともlowerCamelCaseにし、呼び出しでは常に`pages.home.greeting`のような完全なキーを使う。
最上位は文言の持ち主ごとに固定し、中の構造はその持ち主の構造をそのまま写す。

| 最上位 | 持ち主 | 中の構造とキーの決め方 |
| --- | --- | --- |
| `app` | アプリ自体 | 平ら。`name`などアプリ全体の属性 |
| `validation` | Zodスキーマ | 平ら。失敗した条件の名前（`required`・`invalidEmail`・`maxLength`）。項目名やモデル名は入れず、上限などは`{max}`の引数で渡す |
| `actions` | 操作ボタン | 平ら。動詞（`create`・`save`・`cancel`・`search`・`signOut`）。目的語は付けない |
| `errors` | Server Action・フォーム | 平ら。原因の名前（`authenticationRequired`・`notFound`・`saveFailed`）。HTTPステータスや例外名で命名しない |
| `models.<model>` | Prismaのモデル | `name`・`fields.<field>`・`enums.<field>.<value>`の3種類だけ。`<model>`はPrismaのモデル名をlowerCamelCaseにしたもの、`<field>`はPrismaのフィールド名、`<value>`は保存する値そのもの |
| `components.<component>` | `src/components`の部品 | `<component>`はファイル名をlowerCamelCaseにしたもの（`data-table` → `dataTable`）。中のキーは部品が受け取る`labels`のprop名と一致させる |
| `pages.<segment>...` | `src/app`の各ページ | ルート構成を写す。ルートグループと`_`のディレクトリは無視し、動的セグメントはその次のセグメント名で表す（`/connections/[id]/edit` → `pages.connections.edit`）。各ページは`title`、必要なら`description`、その他は画面固有のキー |

```json
{
  "app": { "name": "my-app" },
  "validation": { "required": "入力してください" },
  "actions": { "save": "保存", "signOut": "ログアウト" },
  "errors": { "notFound": "対象が見つかりません" },
  "models": {
    "connection": {
      "name": "接続",
      "fields": { "name": "名前", "kind": "種別" },
      "enums": { "kind": { "trocco": "TROCCO" } }
    }
  },
  "components": {
    "dataTable": { "previous": "前のページ", "next": "次のページ" },
    "emptyContent": { "title": "{name}がありません" }
  },
  "pages": {
    "home": { "title": "ホーム", "greeting": "こんにちは、{name}さん" },
    "connections": {
      "title": "接続",
      "edit": { "title": "接続の編集" }
    }
  }
}
```

置き場所は次の順で決める。

1. Zodのメッセージは`validation`。
2. Prismaのモデル・フィールド・許可値の表示名は`models`。
3. `src/components`の部品がpropsで受け取る文言は`components`。`src/app`配下の`_components`は`pages`。
4. 2つ以上の画面で同じ文言を使うなら、動詞は`actions`、失敗は`errors`。
5. それ以外はその画面の`pages`。

`pages`の中に同じ文言が2か所できたら3か4へ移す。`pages`に`shared`や`common`のような横断キーは作らない。
「接続を作成」のように目的語を含む文言は`actions`ではなく`pages`に置く。ページの`title`とモデルの`name`が同じ文言になっても、それぞれの持ち主の関心として別に持つ。
ICUの引数名は値の意味で付け、使う側で定義する（`"{page, number}ページ目"`）。
`components`の文言にモデル名や項目名を含める場合は、`"{name}がありません"`のように引数にし、呼び出し側が`models`の文言を渡す。部品ごと・画面ごとに同じ文を書き直さない。

## 翻訳の呼び出し

非同期Server Componentでは次のように使う。

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const translate = await getTranslations();
  return <h1>{translate("pages.home.greeting", { name: "太郎" })}</h1>;
}
```

Client Componentでは次のように使う。`useTranslations`は非asyncのServer Componentでも利用できる。

```tsx
const translate = useTranslations();
translate("pages.home.greeting", { name: "太郎" });
```

翻訳関数の変数名は`translate`に統一し、`t`などへの短縮は禁止する。
`getTranslations`・`useTranslations`に名前空間を指定することも禁止する。
呼び出し側に完全なキーを残すことで、翻訳処理と特定の文言の使用箇所をgrepで検索できるようにする。

翻訳は表示側で行い、[Baseのusecases・domain](../../base/directory-structure.md)にnext-intlへの依存を持ち込まない。

フォームの検証エラーは[React Hook Formの方針](react-hook-form.md#i18nとuseformの接続)に従い、翻訳済みの文言をZodへ渡す。
