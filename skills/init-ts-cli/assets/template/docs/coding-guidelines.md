# コーディング方針

TypeScriptの命名と配置を揃え、上から読んで役割と処理が分かるようにする。
層同士の依存関係は[ディレクトリ設計](directory-structure.md#依存関係)に従う。

## 関数と型

classは定義しない。データは型・インターフェース、処理は関数で表し、依存は引数で渡す。
外部ライブラリが提供するclassの利用は、この制限の対象にしない。

## 命名と配置

| 対象 | 基本方針 |
| --- | --- |
| ファイル・ディレクトリ | `kebab-case` |
| 関数・変数 | `camelCase` |
| 型・インターフェース | `PascalCase`。インターフェースに`I`接頭辞は付けない |
| export | 基本はnamed export。cittyのコマンド定義など、用途に合わせてdefault exportを使う |
| 型・定数 | 関連する処理と同じファイルに置く。種類だけで`types/`・`constants/`へ分散させない |
| 補助関数 | まず使うファイル内に置き、必要なものだけexportする |
| `index.ts` | CLIの取りまとめなど、役割がある場合に使う。単なる再export用には増やさない |

## 可読性

### 並び順

ファイル・インターフェース・定数のいずれも、**理解に必要なものを先に、参照用のものを後に置く**。
上から読めば概要が分かり、下に進むほど詳細になるように構成する。
この原則はexportするものの中、ファイル内だけで使うものの中でも適用する。

### ファイル内

1. imports
2. 公開APIの理解に必要な型・定数
3. export関数
4. ファイル内だけで使う関数
5. ファイル内だけで使う参照用データ（マップテーブルなど）

`Args`など、関数シグネチャの理解に必要な型は、exportの有無によらず関数の前に置く。
補助関数はexport関数内での出現順を基本にし、その補助関数が呼ぶ関数を直後に置いて詳細へ読み進められるようにする。
実行時の初期化順序が必要な場合は、それを優先する。

### 型・インターフェースのフィールド

ドメインの自然な順序に従う。

識別子 → コア属性 → 条件・コンテキスト → 詳細・メタデータ

### enum的な定数・マップテーブル

階層の高低、強度の軽重、公式の番号順など、ドメイン固有の序列に従う。
マップテーブルのキー順は、対応するconst定義の順序と一致させる。

## コメント

**コードはWhatを、コメントはWhyを語る。** 名前から読み取れることは繰り返さない。
説明が必要なら、まず名前や構造で表現できないか考え、コードだけでは伝わらない理由や前提がある場合に書く。

- 意味が自明でない値の根拠
- 外部のバグや非自明な仕様に合わせている理由
- 複数の選択肢の中から、その方法を選んだ理由
- 非自明な変換の意図

型だけでは伝わらない意味を補う具体例も書ける。
例えば`Record<string, string>`が何と何の対応なのかを、名前や型で十分に表現できない場合など。
