# next-intlの初期設定

表示文言はnext-intlで管理する。まず日本語だけを使い、言語別URLは設けない。
`next-intl`を実行時依存へ追加し、[依存管理の方針](../../base/pnpm-workspace.md)に従って採用版を完全固定する。

```text
messages/
  ja.json
src/
  i18n/
    request.ts
    global.d.ts
```

`src/i18n/request.ts`：

```ts
import { getRequestConfig } from "next-intl/server";
import messages from "../../messages/ja.json";

export default getRequestConfig(async () => ({
  locale: "ja",
  messages,
}));
```

日本語固定なので、固定パスで読み込む。`src/i18n/request.ts`は公式の自動検出対象を使う。
日本語の選択とタイムゾーンは別の判断。日時を表示する場合は、サービスの要件に合わせて`timeZone`も指定する。

[文言と呼び出しの規約](../implementation/i18n.md)に従ってメッセージを追加する。

## Next.js設定と型安全性

既存の`next.config.ts`をpluginで包む。次は[Docker向けのstandalone設定](docker.md)も含めた例。

```ts
import type { NextConfig } from "next";
import createNextIntlPlugin from "next-intl/plugin";

const nextConfig: NextConfig = {
  reactCompiler: true,
  output: "standalone",
};

const withNextIntl = createNextIntlPlugin({
  experimental: {
    createMessagesDeclaration: "./messages/ja.json",
  },
});

export default withNextIntl(nextConfig);
```

`src/i18n/global.d.ts`で型を拡張する。

```ts
import type messages from "../../messages/ja.json";

declare module "next-intl" {
  interface AppConfig {
    Locale: "ja";
    Messages: typeof messages;
  }
}
```

[tsconfig](typescript.md)の`compilerOptions`へ次を追加する。

```json
{
  "allowArbitraryExtensions": true
}
```

| 設定 | 意味・採用理由 |
| --- | --- |
| `AppConfig.Locale` | 許可する言語を日本語に限定する |
| `AppConfig.Messages` | メッセージから名前空間・キーの型を得る |
| `createMessagesDeclaration` | 文言を文字列リテラルの型として保持し、埋め込み引数も検査する |
| `allowArbitraryExtensions` | JSONに対応する生成宣言をTypeScriptが解決できるようにする |

JSONの型拡張だけでは、文言の値は一般の`string`になり、`{name}`などの引数を型から取得できない。
宣言生成は実験的機能だが、キーだけでなく引数の渡し忘れも検出するため採用する。更新時には生成と型検査の挙動も確認する。

生成される宣言は手編集せず、`.gitignore`へ次を追加する。

```gitignore
/messages/*.d.json.ts
```

宣言は`next dev`・`next build`・`next typegen`で生成される。
既存の`typecheck: "next typegen && tsc --noEmit"`を使い、初回も生成してから型チェックする。エディターで型が揃わない場合も、先に型生成を実行する。
生成宣言を直接importせず、元のJSONを参照する。

## 依存のinstall script

型宣言の生成に使われる`@parcel/watcher`・`@swc/core`も、[Baseの`allowBuilds`方針](../../base/pnpm-workspace.md)に従って判断する。
次はLinux/arm64で配布済みのネイティブバイナリを使う構成。既存の`allowBuilds`へ追加する。

```yaml
allowBuilds:
  "@parcel/watcher@2.6.0": false
  "@swc/core@1.16.2": false
```

watcherのscriptはソースからのビルド用、SWCのscriptはネイティブバイナリの確認と、不足時にnpmでWasm版を導入するフォールバック用。
この構成ではscriptを実行しない。導入する環境でも、型生成・型チェック・本番ビルドと両者のネイティブ処理が動くことを確認する。
バージョン・実行環境が変わった場合は再確認し、`strictDepBuilds`を無効化して通さない。

## 初期設定の範囲

日本語固定なので、`[locale]`・言語切り替え用のproxy・routing設定は追加しない。
多言語化するときにルーティングを検討し、各言語のキーと引数の整合性も確認する。日本語の型定義だけで他言語の整合性まで保証されるわけではない。

[Dockerの許可リスト](docker.md#dockerignore)には`messages/`を含める。型宣言はビルド時に生成する。

## Providerと利用方法

root layoutで`NextIntlClientProvider`を組み合わせる。
[Mantineのlayout設定](mantine.md)のbody部分は、次のようになる。

```tsx
import { NextIntlClientProvider } from "next-intl";

<NextIntlClientProvider>
  <MantineProvider defaultColorScheme="light">
    {children}
  </MantineProvider>
</NextIntlClientProvider>
```

layoutはServer Componentのままにし、`html`の`lang`は`ja`にする。
Server側から描画するProviderはrequest設定を継承するため、locale・messagesを改めて取得して渡す必要はない。
最初は全メッセージを渡す標準構成を使う。クライアントへ転送されるため、文言が増えて負荷が問題になったら、渡す名前空間を絞るかサーバーで翻訳済みの値を渡す。
